# 分账问题与排查

本文档整理接入微信支付分账功能时遇到的问题、原因与处理方式，便于后续排查与新人接入。

---

## 1. 分账接收方关系不存在（PARAM_ERROR）

**现象**：请求分账接口返回 400，错误信息：

```json
{ "code": "PARAM_ERROR", "message": "分账接收方关系不存在，请检查参数中每个接收方的关系。" }
```

**原因**：使用 `PERSONAL_OPENID`（个人 openid）作为分账接收方时，必须先调用微信「添加分账接收方」接口建立接收方关系，否则不能参与分账。

**处理**：

- **自动处理**：本模块在 `createProfitsharingOrders` 中会对每个 `PERSONAL_OPENID` 接收方先调用 `addProfitsharingReceiver`，再发起分账。确保接收方先添加再分账。
- **手工添加**：可调用 `POST /api/v1/pay/split/receiver` 接口，传入 `type: PERSONAL_OPENID`、`account: openid`，提前将某用户添加为分账接收方。
- **注意**：添加后需等待微信审核，接收方状态变为 **EFFECTIVE** 后才能参与分账；若刚添加就分账可能仍报此错，可稍后重试或到商户平台查看接收方状态。

---

## 2. 查询分账结果返回 405（Method Not Allowed）

**现象**：调用「查询分账结果」接口时 HTTP 状态码 405，响应 body 为空。

**原因**：可能为以下之一：

- **商户类型与接口不匹配**：若为**服务商/电商子商户**，应使用电商分账查询接口  
  `GET /v3/ecommerce/profitsharing/orders`，并传 `sub_mchid`；当前实现为普通商户接口 `GET /v3/profitsharing/orders`。
- **代理/网关**：前置代理或网关改写或限制了请求方法，导致微信侧返回 405。

**处理**：

- 确认商户类型：普通商户用现有接口；服务商/电商子商户需改为电商分账查询接口并传 `sub_mchid`。
- 在无代理环境下直连微信重试，或检查代理配置。
- 可尝试使用 wechatpay-node-v3 的 `pay.query_profitsharing_orders(transaction_id, out_order_no)` 与自实现 GET 对比，排除请求构造差异。

---

## 3. 分账请求实际失败但日志显示「请求成功」

**现象**：微信返回 400/4xx，但日志里仍打印「[createProfitsharingOrders] 请求成功」。

**原因**：wechatpay-node-v3 在 HTTP 4xx/5xx 时**不抛异常**，而是返回形如 `{ status: 400, error: "{\"code\":\"...\",\"message\":\"...\"}" }` 的对象，原逻辑未判断 `res.status`，一律当成功处理。

**处理**：已在 `createProfitsharingOrders` 中增加对 `res.status >= 400` 的判断：失败时解析 `res.error` 中的 code/message，打「请求失败」日志并 `throw new Error(...)`，由 SplitProcessor 捕获并将订单标为分账失败，同时不再误写 Redis 的 doneKey。

---

## 4. 请求分账时接收方字段用 openid 还是 account

**现象**：不确定请求体里接收方应传 `openid` 还是 `account`。

**原因**：微信支付 V3 文档中，分账接收方列表统一使用 **account** 字段：`MERCHANT_ID` 时 account 为商户号，`PERSONAL_OPENID` 时 account 为个人 openid（即 openid 的值要放在 account 里）。

**处理**：代码已统一使用 `base.account`：`PERSONAL_OPENID` 时 `base.account = r.openid`，`MERCHANT_ID` 时 `base.account = r.account`。不再使用 `base.openid`。

---

## 5. 下单时报「请求中含有未在API文档中定义的参数」/ profit_sharing

**现象**：创建 JSAPI 预支付订单时返回 400：

```json
{ "code": "PARAM_ERROR", "message": "请求中含有未在API文档中定义的参数", "detail": { "value": ["/body/profit_sharing"] } }
```

**原因**：分账标记应放在 **`settle_info`** 对象下，而不是 body 顶层。body 顶层传 `profit_sharing` 不在 JSAPI 下单接口文档定义中，会被微信拒绝。

**正确写法**：在 JSAPI 下单请求体中传：

```json
"settle_info": { "profit_sharing": true }
```

**本模块**：`createJsapiPrepay` 中已使用 `settle_info: { profit_sharing: true }` 标记分账订单，无需配置开关。

---

## 6. 非分账订单不支持分账（INVALID_REQUEST）

**现象**：请求分账接口返回 400：

```json
{ "code": "INVALID_REQUEST", "message": "非分账订单不支持分账" }
```

**原因**：只有**分账订单**才能请求分账。若创建支付订单（JSAPI/Native 等）时未声明为分账订单，支付成功后对该笔订单调用分账会报此错。

**处理**：需在创建 JSAPI 预支付订单时传 `profit_sharing: true`。本模块在配置 `pay.profitSharing === true` 时才会传该参数（见 `createJsapiPrepay`）。仅对**此后新创建**的支付订单生效；此前已支付的订单无法改为分账订单，属于微信侧限制。若下单传 `profit_sharing` 会报「未在API文档中定义的参数」，见上文第 5 条。

---

## 7. 添加分账接收方已存在（RECEIVER_EXIST）

**现象**：调用「添加分账接收方」时返回「接收方已存在」。

**处理**：本模块将 `RECEIVER_EXIST` 或错误信息包含「已存在」时视为成功（幂等），不抛错，直接继续后续流程（如发起分账）。无需额外处理。

---

## 流程小结

1. **开通分账**：商户平台开通分账能力。
2. **添加接收方**：对 `PERSONAL_OPENID` 先调用添加分账接收方（本模块在发起分账前自动添加，也可通过 `POST /api/v1/pay/split/receiver` 手工添加）。
3. **下单时标记分账**：JSAPI 下单传 **`settle_info: { profit_sharing: true }`**（见 `createJsapiPrepay`），不能传 body 顶层 `profit_sharing`。
4. **支付成功后请求分账**：由 SplitProcessor 调用 `createProfitsharingOrders`，内部会先添加接收方再请求分账。
5. **查询结果**：通过「查询分账结果」接口或分账动账回调更新订单分账状态。
